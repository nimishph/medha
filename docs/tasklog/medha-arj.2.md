## Objectives

**Explicit (from the backlog):** Add `DecisionCase` (id, parentId, condition, decision:
apply|ignore|probability, evidence) and `DecisionEpisode` (parentId?, condition, decision) to
medha-core. Add `newDecisionCaseId(key, random?)` producing `entity-id-dec-<5-char-alnum>`, with
`entityKeyString` mixed into the seed so ids don't collide across concurrent hosts. Add
`foldDecisionTree(episodes, key): DecisionCase[]` built only from decision episodes for that key,
independent of the trust fold.

**Inferred:** The backlog description for `DecisionEpisode` didn't list a `caseId` field, but
`medha-arj.5`'s CLI shape (`medha <kind> <id> decision <condition> <decision> [--parent
<case-id>]`) and the "latest-write-wins per case id on edit" acceptance criterion both require the
episode to carry which case it targets. I inferred `DecisionEpisode.caseId: string` (required, not
optional) — generated by the caller via `newDecisionCaseId` before the episode is submitted (never
by the fold itself, which must stay pure and replay-deterministic; see `[[medha-arj.1]]`'s
no-randomness-in-fold precedent). Submitting the same `caseId` again is how an "edit" happens.
`DecisionCase` also grew an `ema: EmaState` field beyond the backlog's literal list — needed by
`[[medha-arj.3]]`'s per-branch trust scoring, added here since the type is shared.

**Spec/doc citation:** `bd show medha-arj.2`; no spec doc section yet (`medha-arj.7` will add one).

## Impact & consequences

**Positive:** Unblocks `[[medha-arj.3]]` (done alongside), `[[medha-arj.5]]`/`.6` (CLI + render),
and `.7`/`.8` (docs + conformance vectors).

**Risk surface:** `newDecisionCaseId`'s default (`Math.random`) makes case-id generation
non-deterministic unless a caller passes a seeded RNG — fine for real usage (CLI/agent write
paths), but any test or replay scenario needing determinism must pass one explicitly (as the tests
here do via `mulberry32`).

**Why this approach:** Considered generating the id inside `foldDecisionTree` itself when a
`DecisionEpisode` arrives without a `caseId`, but that would make the fold impure (it would need
to invent state depending on when it runs, breaking replay-determinism — the exact property
`[[medha-arj.1]]` and the rest of the episode log design protect). Generating the id at the write
plane and always requiring it on the episode keeps the fold pure.
